작성일: 2026-08-29
상태: 승인 대기 → 승인 후 구현 계획(writing-plans)으로 이행

---

## 1. 한 줄 요약

로컬 전용 PWA 암기 앱. 덱에 카드를 넣고, 객관식으로 반복해서 풀고, 틀린 것만 다시 푼다.

## 2. 목표와 범위

**목표.** 단어장·기출문제·기술면접 질문처럼 성격이 다른 암기 대상을 **하나의 앱, 몇 개의 지정된 카드 유형**으로 다룬다. 유형을 느슨하게 열어두되 형태는 고정해서, 외부에서 JSON으로 만들어 올릴 수 있게 한다.

**사용자.** 지금은 1인, 단일 기기. 계정·서버 없음. 데이터는 브라우저 IndexedDB에만 존재한다.

**나중에 열어둘 지점** (지금은 구현하지 않음):
- 기기 간 동기화 — `db/` 레이어가 유일한 저장소 접점이므로 여기만 교체하면 된다
- 카드 유형 추가(빈칸 채우기 `cloze` 등) — `types/`에 유형 하나 추가하는 비용
- 간격반복(SRS) — 현재 출제 정렬을 스케줄러로 교체
- AI 카드 생성 — 이번 범위에서 명시적으로 제외(키 보관 문제와 비용)

**비범위(YAGNI).** 계정/로그인, 서버, 덱 공유·공개, 세션 히스토리·통계 대시보드, 화면 렌더링 테스트, 다국어.

## 3. 데이터 모델

```ts
type Deck = {
  id: string            // nanoid
  name: string
  description?: string  // 덱 단위 메모
  createdAt: number
}

type CardBase = {
  id: string
  deckId: string
  tags: string[]
  explanation?: string  // 개념설명란 — 채점 직후 펼쳐진다
  stats: { right: number; wrong: number; lastSeenAt: number | null }
}

type TermCard = CardBase & {
  type: 'term'
  front: string
  back: string
  distractors?: string[]   // 없으면 같은 덱 다른 카드의 back에서 자동 추출
}

type McqCard = CardBase & {
  type: 'mcq'
  question: string
  choices: string[]        // 2개 이상
  answer: number           // choices의 인덱스
}

type QaCard = CardBase & {
  type: 'qa'
  question: string
  answer: string           // 긴 모범답안
}

type Card = TermCard | McqCard | QaCard
```

`explanation`이 모든 유형에 공통으로 붙는 것이 이 설계의 핵심이다. 채점 직후 "왜 이 답인지"가 그 자리에서 나오므로 별도의 오답노트 화면이 필요 없어진다.

### 진행 중인 세션

```ts
type ActiveSession = {
  deckId: string
  cardIds: string[]                                  // 확정된 출제 순서
  cursor: number                                     // 다음에 풀 인덱스
  results: { cardId: string; correct: boolean }[]
  startedAt: number
}
```

IndexedDB에 **한 건만** 유지한다. 매 문제 채점 직후 덮어쓰고, 세션이 끝나면 삭제한다. 다른 덱으로 학습을 시작하면 "진행 중인 세션이 있습니다, 버릴까요?"만 확인한다. 세션 히스토리와 만료 정책은 두지 않는다 — 필요해지면 이 레코드를 배열로 바꾸는 일이다.

### 유형별 JSON 임포트 스키마

임포트 파일은 `{ deck, cards[] }` 한 덩어리다. `id`·`stats`·`deckId`는 임포트 시 앱이 채우므로 파일에 쓰지 않는다.

```json
{
  "deck": { "name": "정보처리기사 1과목", "description": "2024 기출" },
  "cards": [
    {
      "type": "term",
      "front": "cohesion",
      "back": "응집도 — 모듈 내부 요소들이 하나의 목적에 얼마나 모여 있는가",
      "tags": ["소프트웨어설계"],
      "explanation": "결합도(coupling)와 짝으로 외운다. 응집도는 높을수록, 결합도는 낮을수록 좋다."
    },
    {
      "type": "mcq",
      "question": "다음 중 응집도가 가장 높은 것은?",
      "choices": ["우연적 응집도", "논리적 응집도", "기능적 응집도", "시간적 응집도"],
      "answer": 2,
      "explanation": "기능적 > 순차적 > 교환적 > 절차적 > 시간적 > 논리적 > 우연적 순."
    },
    {
      "type": "qa",
      "question": "React에서 useMemo를 언제 쓰는가?",
      "answer": "계산 비용이 큰 값이 매 렌더마다 다시 계산되는 것을 막을 때. 참조 동일성이 자식의 memo 비교에 영향을 줄 때도 쓴다. 대부분의 경우 없이도 충분하며, 프로파일링으로 병목을 확인한 뒤 붙인다.",
      "tags": ["react", "면접"]
    }
  ]
}
```

앱의 임포트 화면에 이 스키마 설명과 유형별 샘플을 그대로 싣고, 샘플 파일을 내려받을 수 있게 한다. 외부(에디터·다른 AI)에서 만들어 올리는 것이 1차 사용 경로다.

**검증은 zod로 하고, 타입 정의와 스키마는 같은 소스에서 나온다** (`z.infer`). 계약이 두 벌이 되면 반드시 어긋난다.

## 4. 학습 루프

```
덱 선택 → 출제 순서 확정 → 한 문제씩 풀기 → 결과 → [틀린 것만 다시 풀기] → …
```

**출제 순서.** 셔플하되 `wrong > right`인 카드를 앞쪽으로 보낸다. 정렬 한 줄로 SRS 효과의 대부분을 얻는다.

**유형별 출제.**

| type | 화면 | 채점 |
|---|---|---|
| `term` | 4지선다. 보기는 `distractors`가 있으면 그것, 없으면 같은 덱 다른 카드의 `back`에서 무작위 추출 | 자동 |
| `mcq` | `choices` 그대로, 순서만 셔플 | 자동 |
| `qa` | 질문 → 생각 → 뒤집기 → 모범답안 | 자가채점(알았음/몰랐음) |

덱에 카드가 4장 미만이면 `term`의 보기를 채울 수 없다. 이때는 보기 수를 있는 만큼 줄인다(최소 2). 2장도 안 되면 그 카드는 `qa`처럼 뒤집기로 출제한다.

**채점 직후** 정답 표시와 함께 `explanation`을 펼친다. 틀렸을 때는 자동으로, 맞았을 때는 접힌 채로 둔다.

**결과 화면**에서 `틀린 것만 다시 풀기`를 누르면 그 카드들로 새 세션을 만든다. 다 맞힐 때까지 반복할 수 있고, 다 맞히면 버튼이 사라진다.

`stats.right/wrong`은 세션 종료 시점이 아니라 **매 채점마다** 누적한다. 중간 이탈해도 푼 만큼은 남는다.

## 5. 화면

| 화면 | 내용 |
|---|---|
| 홈 | 덱 목록(카드 수, 최근 정답률), 덱 추가, 진행 중 세션 `이어하기` 배지 |
| 덱 상세 | 카드 목록·검색·태그 필터, 카드 추가/편집/삭제, 임포트·익스포트, `학습 시작` |
| 학습 세션 | 상단 진행바, 유형별 문제 렌더, 즉시 채점, `explanation` 펼침 |
| 결과 | 맞은 수/틀린 수, `틀린 것만 다시 풀기`, 덱으로 |
| 임포트 | 대량 붙여넣기 / JSON 파일 / 유형별 스키마 설명·샘플 다운로드 |

**대량 붙여넣기.** 텍스트를 통째로 붙이고 카드 구분자(줄바꿈/빈 줄)와 앞뒤 구분자(탭/쉼표/사용자 지정)를 고른다. 미리보기로 몇 장이 파싱됐는지 보여준 뒤 확정한다. `term` 유형만 지원한다 — `mcq`·`qa`는 구조가 있어 JSON 경로가 맞다.

## 6. 디자인 시스템

방향: **집중형 미니멀.** 문제 텍스트가 주인공이고, 그 외에는 아무것도 시선을 가져가지 않는다. 라이트/다크 모두 지원하고 **수동 토글**을 둔다(초기값은 `prefers-color-scheme`, 선택은 localStorage에 남는다).

**라이트는 순백이 아니라 아이보리 계열**로 간다. 암기 앱은 한 번에 20~40분씩 텍스트를 응시하는 앱이라, 흰 배경의 대비가 그대로 피로가 된다.

```css
:root {                        /* light — ivory */
  --bg:        #FAF6EC;
  --surface:   #FFFCF5;
  --text:      #2A2622;
  --text-mute: #6E6459;
  --border:    #E6DFD0;
  --accent:    #A9552B;        /* 테라코타 — 아이보리와 같은 난색 계열 */
  --ok:        #2F7A46;
  --bad:       #B0362C;
}
:root[data-theme="dark"] {
  --bg:        #1A1815;
  --surface:   #232019;
  --text:      #ECE5D8;
  --text-mute: #9A9080;
  --border:    #37322A;
  --accent:    #E0996B;
  --ok:        #63B37E;
  --bad:       #E0796E;
}
```

- **타이포.** 웹폰트 없이 시스템 스택(`system-ui, -apple-system, "Apple SD Gothic Neo", "Segoe UI", sans-serif`). 스케일은 4단계(`13 / 15 / 18 / 24px`)만 쓴다. 문제 텍스트는 본문보다 한 단 크다.
- **스페이싱.** 4px 배수, `4 / 8 / 12 / 16 / 24 / 32`.
- **모서리.** 8px 하나. 카드만 12px.
- **그림자 없음.** 면 구분은 `--border`와 `--surface`로만 한다.
- **모션.** 정답 공개와 카드 전환에만, 150ms. `prefers-reduced-motion`을 존중한다.

**공통 컴포넌트** (병렬 개발 전에 확정): `Button`(primary/ghost/danger), `Card`, `Input`, `Textarea`, `Select`, `Modal`, `ProgressBar`, `Badge`, `EmptyState`, `Toast`.

> **개발 게이트.** 이 토큰과 컴포넌트, 그리고 5개 화면 목업을 사용자가 눈으로 확인하고 승인한 뒤에야 병렬 구현에 들어간다. 디자인 없이 세 에이전트를 풀면 버튼 세 종류가 나오고, 통합 비용이 병렬로 아낀 시간을 넘는다.

## 7. 아키텍처

```
src/
  types/     Card·Deck 정의 + zod 스키마. 타입과 임포트 검증이 같은 소스
  db/        Dexie 스키마 + CRUD. 저장소를 만지는 유일한 곳(= 나중 동기화의 유일한 접점)
  ui/        공통 컴포넌트와 토큰
  deck/      홈·덱 상세 화면
  study/     세션 엔진(출제 순서·보기 생성·채점·재출제) + 세션/결과 화면
  import/    붙여넣기 파서, JSON 임포트·익스포트, 스키마 안내 화면
  app/       라우팅, 테마 프로바이더
```

**스택.** Vite + React + TypeScript / Dexie(IndexedDB) / zod / vite-plugin-pwa / vitest.

**의존 방향은 한 방향이다.** `deck`·`study`·`import`는 `types`·`db`·`ui`에만 의존하고 서로를 참조하지 않는다. 이 규칙이 병렬 개발의 전제이자, 나중에 유형을 추가할 때 손댈 곳을 좁히는 장치다.

**PWA.** vite-plugin-pwa로 앱 셸 프리캐시 + 설치 매니페스트까지만. 데이터가 IndexedDB에 있으므로 오프라인은 부수 효과로 따라온다.

## 8. 에러 처리

**임포트가 유일하게 진짜 실패하는 지점이다.** zod 검증 실패는 항목 인덱스와 이유를 붙여 목록으로 보여준다(`3번째 항목: answer가 choices 범위를 벗어남`). 그 다음 **통과분만 넣기 / 전부 취소**를 사용자가 고른다. 200장 중 3장 때문에 전부 버리게 만들지 않는다.

그 밖:
- IndexedDB 접근 불가(사파리 프라이빗 등) → 첫 화면에서 한 번 경고하고, 저장이 안 된다는 사실을 명시한다
- 세션 자동 저장 실패 → 재시도하지 않는다. 다음 채점에서 어차피 덮어쓴다
- 잘못된 경로 → 홈으로

## 9. 테스트

vitest로 **로직이 실제로 있는 세 군데만** 검증한다.

- `study/` — 출제 순서 정렬, 오답 재출제, `term` 보기 추출(덱 카드가 4장 미만·2장 미만인 경계 포함), 유형별 채점
- `import/` — 붙여넣기 파서(구분자 조합), zod 검증의 성공·실패·부분 성공
- `db/` — 스키마 마이그레이션(fake-indexeddb)

화면 렌더링 테스트는 쓰지 않는다. 로컬 전용 5화면 앱에서는 유지비만 나간다.

## 10. 개발 순서와 멀티 오케스트레이션

이 프로젝트는 **orca 멀티 오케스트레이션 실습을 겸한다.** 분할은 그 목적에 맞춰 잡되, 병렬로 만들면 충돌하는 것(계약·디자인)은 앞으로 뺀다.

### 1단계 — 선행 (단독)

병렬 워커들이 공유하게 될 것을 전부 확정한다.

1. 프로젝트 스캐폴딩(Vite + TS + PWA + vitest)
2. `types/` — 카드 유형과 zod 스키마
3. `db/` — Dexie 스키마와 CRUD
4. `ui/` — 토큰과 공통 컴포넌트
5. 5개 화면 목업
6. 라우팅 껍데기

### 2단계 — 디자인 확인 게이트 (사용자)

목업과 토큰을 실제로 띄워서 승인받는다. **여기서 통과하지 못하면 병렬로 넘어가지 않는다.**

### 3단계 — 병렬 (orca 워크트리 3개)

| 워커 | 범위 | 산출물 |
|---|---|---|
| A | `deck/` | 홈, 덱 상세, 카드 CRUD 화면 |
| B | `study/` | 세션 엔진 + 세션·결과 화면 + 엔진 테스트 |
| C | `import/` | 붙여넣기 파서, JSON 임포트·익스포트, 스키마 안내 + 파서 테스트 |

각 워커는 `types`·`db`·`ui`를 **읽기만** 한다. 이 파일들을 고쳐야 하는 상황이 생기면 직접 고치지 않고 코디네이터에게 올린다(계약 변경은 셋 모두에게 영향을 준다).

**실행 경로.** `orca orchestration run-create`로 Run을 만들고, 워커마다 `worktree create` → `orchestration task-create` → `orchestration worker-start --agent codex --model <luna에 해당하는 모델 id>`. Codex 계정은 이 호스트에 이미 활성 상태(`orca account list`로 확인됨).

> **킥오프 시 검증할 것:** `luna`가 `--agent`/`--model` 중 어느 인자의 어떤 값에 대응하는지. CLI 스키마(`orca agent-context`)에서는 잡히지 않았다. 워커 하나를 먼저 띄워 확인한 뒤 나머지를 푼다.

### 4단계 — 통합

세 브랜치를 순서대로 머지하고(`import` → `deck` → `study`), 실제 브라우저에서 전 루프를 한 번 통과시킨다: 덱 생성 → JSON 임포트 → 학습 → 중간 이탈 → 이어하기 → 오답 재출제 → 익스포트.

### 기록
