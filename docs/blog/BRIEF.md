> **이 문서를 읽는 에이전트에게.** 이 폴더는 *Memonowz* 라는 앱을 만든 기록이고, 목표는 그 과정을 블로그 글로 쓰는 것이다. 이 파일 하나에 글을 쓰는 데 필요한 사실·서사·이미지 지침이 전부 들어 있다. 더 깊은 근거가 필요할 때만 같은 폴더의 `PROCESS.md` 를 열어라. **여기 없는 숫자나 사건은 지어내지 마라** — 없으면 없는 대로 쓰거나, `PROCESS.md` 와 `devlog-excerpt.md` 에서 확인해라.

## 1. 한 문장 요약

암기용 PWA 하나를, **Claude는 설계와 검증만 하고 코드는 전부 Codex 워커가 쓰는** 구조로 만든 기록. 계획 확정부터 통합 완료까지 45분, 그중 병렬 구간이 13분 30초.

## 2. 독자와 목적

**독자.** AI 코딩 에이전트를 실제로 써서 뭔가 만들어본 개발자. 멀티 에이전트 오케스트레이션이 실무에서 값이 나오는지 궁금한 사람.

**목적.** "에이전트 여러 개 돌렸더니 빨랐다" 류의 글이 아니다. **분할이 어디서 새고, 무엇이 그걸 막았고, 자동 검증이 무엇을 못 잡는지**를 실제 사례로 보여주는 글이다.

**쓰지 말아야 할 톤.** 도구 홍보, 과장("혁명적", "게임체인저"), 실패 숨기기. 아래 6절의 실패 목록은 반드시 글에 들어가야 한다. 이 글의 신뢰성이 거기서 나온다.

## 3. 글의 논지 (이 셋을 축으로 잡아라)

### 논지 1 — 자동 검증 통과 ≠ 제대로 됨

게이트에서 잡은 결함 3건이 **전부 "테스트 통과 + 빌드 성공" 상태에서 나왔다.**

| 게이트 | 잡은 것 | 어떻게 잡았나 | 당시 상태 |
|---|---|---|---|
| A | 계획서의 `deckSchema` ↔ 코드의 `deckInputSchema` 불일치 | `grep` 으로 export를 뽑아 계획서와 한 줄씩 대조 | 테스트 12개 통과 |
| A | 계약 목록에서 누락된 `getCard` | 같은 대조 | 테스트 12개 통과 |
| B | 폰트 프리캐시 4013 KiB | 빌드 로그의 숫자를 읽음 | 빌드 성공, 앱 정상 동작 |
| B | `index.html` 스캐폴딩 잔재 | 실제 HTML을 열어봄 | 빌드 성공, 앱 정상 동작 |

핵심 문장으로 쓸 만한 것: **무엇을 대조해야 하는지 아는 것은 설계를 들고 있는 쪽만 할 수 있다.**

### 논지 2 — 병렬이 새지 않은 데는 이유가 있다

계약 위반 0건, 병합 충돌 0건은 운이 아니었다. 네 가지가 겹쳤다.

1. **계약(`types`/`db`)을 게이트로 먼저 확정했다.** 세 워커가 짜기 시작한 시점에 계약은 이미 검증을 통과한 상태였다
2. **공유 UI(디자인 토큰 + 공통 컴포넌트)를 선행 단계에서 만들었다.** 워커가 버튼을 새로 만들 이유가 없었다
3. **`CardEditor` 를 `deck/` 가 아니라 `card/` 로 분리했다.** 학습 화면에서도 카드를 고칠 수 있게 하기로 한 순간, 모달이 `deck/` 에 있으면 `study` 가 `deck` 을 참조해서 두 워커가 묶인다
4. **"계약은 너 말고 두 개의 다른 워커가 동시에 보고 짜고 있다"를 태스크에 명시했다.** 금지가 아니라 이유를 줬다

고추론 모델(effort `xhigh`)의 실패 방식은 "못 알아들어서"가 아니라 **빈칸을 스스로 그럴듯하게 메워서**다. 세 워커가 각자 합리적으로 판단하면 통합 시점에 서로 다른 세 개의 합리가 충돌한다. 이 문장은 글의 중심 통찰로 쓸 만하다.

### 논지 3 — 규칙에 예외를 두지 않는 편이 싸다

폰트 프리캐시 보정은 설정 파일 3줄짜리 변경이었다. 코디네이터가 직접 고치는 게 명백히 빨랐지만 워커에 재디스패치했다. `index.html` 정리도 마찬가지다.

**어디까지가 코디네이터의 일인지 매번 판단하는 비용이, 규칙을 예외 없이 지키는 비용보다 크다.** 한 번 "이 정도는 내가"를 허용하면 그 경계를 계속 재협상하게 된다.

## 5. 서사 재료 (사건 6개)

글의 뼈대다. 시간순으로 배치하면 자연스럽게 이야기가 된다.

### 사건 1 — 계획이 뒤집혔다 (설계 단계)

첫 계획은 "선행 단계(계약·공유 UI)는 코디네이터가 직접 구현하고, 마지막에 세 모듈만 병렬로 돌린다"였다.

사용자가 한 줄로 뒤집었다:

> "근데 이러면 멀티 오케스트레이션이 맞나?"

맞는 지적이었다. 그 구조에서는 절반이 단독 작업이고, 워커 셋이 한 층에 나란히 있을 뿐이다. **실제로 순차적이어야 하는 건 `types` 하나뿐**이었다.

이후 최대 8워커 3층 DAG + 태스크별 검증 에이전트 안도 나왔지만 이것도 과했다. 이유: 병렬 폭을 넓히면 워커 토큰은 선형으로 늘지만 **코디네이터의 추적 비용은 그보다 빨리 는다.** 검증 전용 에이전트는 코디네이터가 맥락을 못 들고 있을 때 쓰는 방식인데, 이번엔 코디네이터가 스펙과 계획을 통째로 들고 있어서 같은 맥락을 다시 읽히는 비용만 든다.

최종: Codex 세션 4개(선행 1 + 병렬 3), 검증은 코디네이터가 직접.

### 사건 2 — 성공 신호를 잘못 읽었다 (18:36)

```bash
orca orchestration worker-start --agent codex --model luna --effort high
```

CLI가 `ok: true`, `stage: input_accepted` 를 돌려줬다. 코디네이터(Claude)는 이걸 보고 "모델이 그대로 통했다"고 사용자에게 보고했다. **틀렸다.**

워커 터미널을 읽어보니:

```
The 'luna' model is not supported when using Codex with a ChatGPT account.
```

실제 모델 id는 `gpt-5.6-luna`, effort는 `high` 가 아니라 `xhigh` 였다.

교훈: **CLI가 인자를 받아들인 것과 모델이 실제로 붙은 것은 별개다.** `input_accepted` 는 "입력이 전달됐다"는 뜻이지 "일이 시작됐다"는 뜻이 아니다. 이후로는 기동 직후 반드시 `orca terminal read` 로 실제 출력을 확인하고 보고했다.

### 사건 3 — 코디네이터와 워커의 git 충돌 (18:47)

선행 A가 도는 동안 코디네이터가 블로그용 다이어그램을 커밋하려다 사고가 났다. 실패가 두 겹이었다.

1. 코디네이터의 `git add docs/blog-assets` 가 스테이징된 상태에서 커밋이 `index.lock` 에 걸렸다. **그 인덱스를 워커의 커밋이 그대로 집어삼켰다** — "스캐폴딩" 메시지에 문서 5개만 담긴 커밋이 됐다
2. 그걸 고치려던 `git reset --soft HEAD~1` 이, 워커가 같은 메시지로 만든 **두 번째 정상 커밋**을 되돌렸다. 같은 메시지의 커밋이 둘이라는 걸 확인하지 않은 게 두 번째 실수다

**여기서 중요한 건 워커가 이걸 스스로 감지해서 escalation으로 올렸다는 점이다:**

```
msg_a4328c18e431 [escalation] "Blocked: 동시 Git 커밋 경합으로 Task 1 커밋이 문서 커밋으로 생성됨"
```

워커가 조용히 넘어갔다면 "스캐폴딩 커밋에 스캐폴딩이 없는" 히스토리가 그대로 남았을 것이다. **blocked를 올릴 수 있는 채널이 있다는 게 실제로 값어치를 낸 지점이다.**

원인은 선행 단계를 `--worktree current`(코디네이터와 같은 워크트리)로 돌린 대가다. 별도 워크트리로 뺐다면 없었을 문제지만, 그러면 세 병렬 워커가 전부 그 브랜치를 base로 잡아야 해서 더 복잡해진다. **트레이드오프를 알고 고른 것이고, 실제로 물린 지점이 여기였다.**

고친 방법: 공통 제약에 `git add -A` 금지, 자기 경로만 명시. 이후 재발 없음.

### 사건 4 — 게이트 A가 계약 불일치를 잡았다 (18:51)

선행 A 완료 시점: 테스트 12개 통과, 빌드 성공, 계획서 밖 의존성 없음. 여기서 멈추지 않고 export 목록을 계획서와 한 줄씩 대조했다.

- 계획서 `Produces` 목록에는 `deckSchema`, 같은 태스크의 코드 블록은 `deckInputSchema`. **계획서 쪽 오류였고 워커가 맞았다**
- `getCard` 가 카드 편집 모달 코드에서 이미 쓰이는데 목록에 없었다. 워커가 알아서 만들어줬지만, **목록에 없는 함수를 병렬 워커가 있다고 가정할 수는 없다**

세 병렬 워커가 이 목록을 보고 짜기 때문에, 여기서 안 고쳤으면 세 곳에서 동시에 어긋났다.

### 사건 5 — 게이트 B가 4MB를 잡았다 (18:59~19:03)

빌드 로그를 읽어보니:

```
precache  283 entries (4013.22 KiB)
```

`@fontsource/ibm-plex-sans-kr` 가 유니코드 범위별 서브셋 **274개, 3.9MB** 를 뿌리는데, 계획서에 적혀 있던 `globPatterns: ['**/*.{js,css,html,woff2,png}']` 가 그걸 전부 프리캐시하고 있었다. 설치 첫 실행에 4MB를 통째로 받는다.

런타임 캐시(`CacheFirst`)로 옮겼다. 한 번 렌더된 서브셋은 캐시에 남아 오프라인에서도 나오고, 아직 본 적 없는 글자 범위만 시스템 폰트로 폴백된다.

```
precache  9 entries (615.12 KiB)
```

같은 게이트에서 `index.html` 도 걸렸다. Vite 템플릿 잔재가 그대로 — `lang="en"`, `<title>memonowz-vite-mad4n1</title>`(브라우저 탭과 PWA 설치 이름에 그대로 나온다), 존재하지 않는 `favicon.svg`(404).

### 사건 6 — 병렬 3워커, 그리고 아무것도 새지 않았다 (19:04~19:19)

워크트리 셋이 갈라졌고 서로의 작업을 보지 못한다. 그게 분할이 새는지 확인하는 조건이다.

`import` 워커가 시작하며 스스로 요약한 문장:

> "계약상 읽기 전용 경로는 건드리지 않으며, `src/import/`만 구현하고 빌드·테스트·브라우저 확인까지 진행하겠습니다."

병합 전 검증에 쓴 명령 (글에 그대로 실어도 좋다):

```bash
# 공유 모듈을 건드렸는가 — 비어 있어야 정상
git diff --name-only main..HEAD -- src/types src/db src/ui src/card src/app vite.config.ts index.html

# 서로를 참조했는가 — 비어 있어야 정상
grep -rn "from '\.\./deck\|from '\.\./study\|from '\.\./import" src/deck src/study src/import
```

셋 다 비었다. CSS 리터럴 색도 0건, 전부 토큰 경유. 병합 순서는 `import` → `deck` → `study`(뒤로 갈수록 참조가 많아서, 충돌 시 늦게 병합되는 쪽에서 고치는 게 싸다). **충돌 0건, 테스트 31개 통과.**

## 6. 실패 목록 (반드시 글에 넣을 것)

이 글의 신뢰성이 여기서 나온다. 축소하거나 생략하지 마라.

- **모델 id를 확인하지 않고 성공을 보고했다** (사건 2)
- **워커와 같은 워크트리에서 `git add -A` 를 썼다** — 인덱스가 섞였다 (사건 3)
- **같은 메시지의 커밋이 둘인 걸 확인하지 않고 `reset --soft HEAD~1` 을 쳤다** — 워커의 정상 커밋을 되돌렸다 (사건 3)
- **계획서에 폰트 프리캐시 패턴을 잘못 썼다** — 게이트에서 잡았지만 애초에 코디네이터가 넣은 것이다 (사건 5)
- **커밋 단위를 강제하지 못했다** — `study` 와 `import` 워커가 계획서의 중간 커밋(엔진만 먼저 커밋)을 건너뛰고 한 커밋으로 합쳤다. 결과는 같지만 지시는 안 지켜졌다. 강제하려면 완료 조건에 커밋 개수를 넣어야 했다
- **브라우저 스크린샷이 도중에 막혔다** — Orca 창이 포커스를 잃으면 캡처가 타임아웃된다. 그래서 `assets/` 의 번호가 05~07에서 비어 있다

## 9. 재현 명령 (글에 실을 코드 블록)

```bash
# Run 만들기
orca orchestration run-create --objective "..." --json

# 태스크 만들기 (--spec 에 태스크 본문)
orca orchestration task-create --run <run_id> \
  --task-title "..." --spec "$(cat spec.txt)" --json

# 현재 워크트리에서 워커 띄우기 (선행 단계)
orca orchestration worker-start --run <run_id> --task <task_id> \
  --worktree current --agent codex --model gpt-5.6-luna --effort xhigh --json

# 새 워크트리로 갈라서 띄우기 (병렬 단계)
orca orchestration worker-start --run <run_id> --task <task_id> \
  --worktree new-child --name memonowz-study \
  --agent codex --model gpt-5.6-luna --effort xhigh --json

# 상태 / 메일함 / 워커 터미널
orca worktree ps
orca orchestration check --run <run_id>
orca terminal read --terminal <handle>
```

**함정 둘 — 이건 꼭 글에 넣어라.**

- `orca terminal wait --for tui-idle` 은 완료 신호로 쓸 수 없다. Codex가 잠깐 멈출 때마다 만족되어서, 작업이 한창인데도 끝난 것처럼 보인다. `dispatch-show` 의 `status` 가 `completed` 가 되는 것을 폴링해야 정확하다
- `worker-start` 의 `stage: input_accepted` 는 완료는커녕 시작 신호도 아니다. `terminal read` 로 실제 출력을 확인해야 한다 (사건 2가 정확히 이것 때문에 생겼다)

## 10. 작성 규칙

- **여기 없는 숫자를 만들지 마라.** 필요하면 `PROCESS.md` 의 부록 표나 `devlog-excerpt.md` 에서 확인해라. 확인이 안 되면 그 문장을 빼라
- **실패를 축소하지 마라.** 6절은 통째로 들어가야 한다
- **도구 홍보처럼 읽히지 않게.** 이 글은 Orca 사용 후기가 아니라, 분할과 검증에 대한 글이다
- **인용은 정확히.** 3절과 5절의 따옴표 안 문장들은 실제 발화·실제 로그다. 다듬지 말고 그대로 써라
- 코드 블록의 명령과 로그 출력도 실제 값이다. 임의로 바꾸지 마라
- 길이는 자유지만, 사건 6개를 다 담으려면 짧지 않을 것이다. 논지 셋 중 하나만 골라 짧게 쓰는 것도 방법이다 — 그 경우 논지 1(자동 검증 ≠ 제대로 됨)이 가장 독립적으로 성립한다
